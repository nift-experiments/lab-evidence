# Concurrency practitioner draft

Diagnostic draft for candidate 7f7e487; 608 supported cells and 11, 506 retained observations passed exact independent coverage/oracle audits. Native futures, promises, worker processes, goroutines and synchronization primitives answer equivalent problems here; they are not identical abstractions and there is no aggregate concurrency score.

For humans and agents maintaining an existing Nift automation project, I would use Nift concurrency for bounded coarse jobs where one runtime and explicit task/result relationships simplify the project. The 100-process fresh median was 98.413 ms versus 132.209 ms Python, 200.007 ms Node, 96.213 ms Bun and 37.260 ms Go. This supports useful bounded orchestration, not universal superiority.

For a new standalone high-fanout tool or concurrent service I would choose Go today, or JavaScript's async model where nonblocking integration fits the problem. Candidate 10k-task scheduling took 20, 311 ms in the persistent boundary versus 14.752 ms Go; 4-worker CPU work took 2, 851 ms versus 15.286 ms Go. Different execution models and interpreted/native scalar work contribute; these are whole-problem results, not isolated scheduler benchmarks. Agents do not make these runtime and memory costs irrelevant.

There are material improvements: 100k four-producer/four-consumer queue work fell from 45, 621 ms historically to 11, 746 ms here, a74.3% lower cross-node trend, while same-host Bun was 56.266 ms. Scheduling and CPU medians improved more moderately. Targeted same-node diagnostics should verify the major change before attributing it entirely to core work.

At the stable 1000-held-task READY checkpoint Nift used 143.625 MiB versus 5.375 MiB Go, 25.5 MiB Bun and approximately 50 MiB Node. The prior Nift checkpoint was 143.5 MiB, so this refresh does not establish a held-task memory improvement. The 10k-task diagnostic was censored when its watchdog exceeded 6 GiB before READY; that is a lower bound, not proof of 8 GiB infeasibility. The primary matrix deliberately preserves the historical exclusion. The runner's13700 MiB text is historical evidence, never a new measured value.

I would reassess Nift for new authored concurrent workflows if task/capture overhead, large fan-out scaling and retained memory become competitive while error propagation, bounded workers and explicit contracts remain reliable. Helpful APIs include clearer task/capture ownership and cancellation/recovery ergonomics, independently validated instead of minimizing syntax. Go's independently deployable compiled artifact remains a concrete operational difference for standalone utilities. For agents, programmatic inspectability and validated semantics matter more than line count, but they must accompany measured feasibility.

Fresh wait 4 memory can include launch accounting; sampled peaks have 5 ms resolution and can include pre-exec snapshots. Stable held-task checkpoints are a separate post-exec scope. No broad memory-efficiency claim is made from unvalidated launch or sampled floors. Long-lived slowdown/recovery conclusions need the separate retained-runtime diagnostic, not the fresh-per-request primary matrix.
