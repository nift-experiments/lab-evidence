# Draft practitioner judgement — build systems

**For human + agent use, I would choose Nift for bespoke procedural builds and mixed Nift-owned projects. For agent-primary maintenance of those authored workflows, I would choose Nift too. For a conventional medium/large native C++ project today, I would choose CMake or Meson with Ninja.** This is an unpublished category judgement; the release candidate remains held because of the confirmed scripting regression and pending build same-node diagnostics.

The audited build engine executes equivalent graphs correctly: all 9,348 observations, action/output/dependency/follow-up gates, full sampling policy and rotated distributions pass. Most current compiler-dominated full-build medians are close to peers: native 10,000 light full is 64,888.828 ms against Make 54,158.282 ms (1.20×). That does not make interactive overhead disappear. Native 1,000 heavy one-worker no-op is 179.197 ms against Ninja 16.839 ms (10.64×). Native 10,000 no-op is 692.382 ms against Ninja 161.857 ms (4.28×). Tiny 10,000 fully dirty is 17,762.305 ms against Make 4,711.695 ms (3.77×).

| Project type | Human + agent choice | Agent-primary choice | Concrete reason |
|---|---|---|---|
| Tiny conventional native build | Make | Make for the straightforward existing rule set | A few source/output rules need little programmable policy; another runtime does not improve that simple contract. |
| Bespoke procedural build or release automation | Nift | Nift | .f policy and explicit artifact/input/order/lifecycle contracts make custom work easier to author and review than complex Make expansion or directly authored Ninja. |
| Website + assets + native helpers + developer tasks already owned by Nift | Nift | Nift | A single project/runtime can express the tested ownership and orchestration without introducing a second state boundary. |
| Conventional medium/large C++ with compiler-discovered headers, toolchains and IDE consumers | CMake/Meson → Ninja | CMake/Meson → Ninja | Reliable compiler dependency ingestion, multi-output action handling, compile databases and toolchain/IDE integrations; lower current no-op cost. |
| Large generated native executor graph with latency-sensitive incremental feedback | Ninja today | Ninja today | Agents can generate explicit Ninja rules; Nift remains materially slower at no-op/small-dirty dispatch and uses more large-graph metadata memory. |

More declarations are not inherently worse for agents. Artifact ownership, ordering, invalidation and lifecycle are different facts, and keeping them independently inspectable can improve automated changes. Redundant values that must be kept synchronized remain a liability. Concise authoring helpers over precise canonical contracts are preferable to collapsing semantics merely to reduce line count.

The benchmark's manually declared include closure and external compiler depfiles are verified; that is not proof of native compiler-dependency ingestion in Nift. Configured 1/2/4 workers work, but a command-line worker override and ensure-vs-force targeting remain authoring gaps. `status`, name queries and `-p` reasons are useful, but complete graph/query/explain and richer multi-output ownership would improve agent verification. The existing repair path is a useful safety boundary, with additional recovery ergonomics still desirable.

Under a mature-Nift counterfactual with reliable compiler dependency ingestion, multi-output actions, ensure/force ergonomics, worker overrides, structured graph introspection, competitive no-op latency and bounded metadata memory, **I see no inherent architectural requirement to retain Ninja as the executor**. Remaining choices could depend on concrete compiler/toolchain/IDE integrations. Today both the engine overhead shown here and those integrations influence my native C++ choice.

Historical screening is mixed. Ninety-six of 97 Nift wall medians are lower cross-node; the largest no-op trend is −53.47%. Tiny 10,000 fully dirty is +33.39% wall/+27.72% CPU/+93.34% maximum-child RSS; large no-op memory also rises despite better elapsed time. Those deserve targeted same-node old/candidate controls, underway separately. None of these cross-node percentages is yet attributed to core. Preserve wins and regressions together; do not let compiler-dominated totals conceal metadata/dispatch tradeoffs.
