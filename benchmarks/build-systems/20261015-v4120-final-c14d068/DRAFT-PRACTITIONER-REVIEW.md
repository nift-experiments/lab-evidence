# Build-system preference and AI-DX — final candidate

**For human-plus-agent bespoke procedural builds and mixed Nift-owned website/assets/helpers/tasks projects, I would choose Nift. For agent-primary maintenance of those workflows, I would choose Nift too. For conventional medium/large native C++ today, I would choose CMake or Meson with Ninja; for a tiny conventional native rule set, Make remains a sensible choice.** These are conditional practitioner judgments, not measured agent productivity results.

AI-DX is a primary axis, separate from speed, memory, correctness and ecosystem fit. Nift's explicit artifact owner, file inputs, execution prerequisites and hook lifecycle let an agent inspect distinct facts without reverse-engineering a compact shell recipe. I value that explicitness. Duplicated values without extra semantics remain a maintenance liability; concise helpers should derive common cases without collapsing ordering and invalidation.

| AI-DX question | Evidence class | Finding and practical limit |
|---|---|---|
| Are intended outputs and executed actions checkable? | Demonstrated by independently audited campaign | All 9,348 observations pass exact action/output hashes, include closure, mutation and follow-up gates. Those independent harness checks are not product-native structured feedback or a guarantee for arbitrary agent edits. |
| Are ownership, ordering and invalidation separate? | Source-inspected frozen adapter; demonstrated generated graphs | Tracked output ownership, tracked `depends`, file-dependency sidecars and build hooks represent distinct facts. The tested explicit graphs work. This does not certify a higher-level consumes-output helper or automatic rejection of every contradictory declaration. |
| Can changes stay bounded? | Demonstrated named-target and subsequent-build cases; qualitative inference | Targeted action/output/follow-up checks make bounded edits reviewable. No autonomous authoring/repair-success comparison was measured, and forced named targeting differs from ensure-if-stale ergonomics. |
| Can an agent inspect state/rebuild reasons? | Candidate source inspection | CLI `info` emits structured project metadata, and `build -p` exposes reasons; these are useful affordances. Complete structured graph/query/explain contracts and a JSON build-result/error stream are not established by this campaign. The CLI's build option parser does not expose `--json`, `--ensure` or `-j`. |
| Are failure and recovery safe? | Demonstrated deletion/failure/target follow-ups; separate task semantic repair evidence | Tested faults and subsequent coherent states are retained. Arbitrary interrupted native-toolchain recovery and comparative autonomous repair safety were not evaluated. |
| Are native-toolchain inputs understood? | Demonstrated manual closure; source/adapter boundary | Generated native include closure and compiler-produced depfiles are checked externally. This is not proof of native Nift depfile ingestion, complete multi-output ownership, toolchain discovery or IDE/compile-database integration. |
| Is the representation easier for agents to transform? | Qualitative inference | Separately meaningful machine-readable fields look easier to inspect/rewrite safely than interleaved implicit rules. No token/time, edit-success or comparative safety score was measured, and competitor affordances were not exhaustively probed. |

Performance can override this authoring preference. Native 1,000 heavy one-worker no-op is 230.478ms against Ninja 18.463ms (about 12.48×). Native 10,000 full is 68.584s against Make 58.543s. Tiny 10,000 fully dirty is 15.846s against Make 6.065s and Ninja 8.820s; Nift's median maximum-child RSS is 17,440KiB against Make 25,252KiB and Ninja 17,456KiB. Treat wall, CPU and maximum-child RSS separately; memory is not summed concurrent usage.

For latency-sensitive generated native graphs, I would use Ninja today. Under a mature-Nift counterfactual with reliable compiler dependency ingestion, multi-output actions, ensure/force ergonomics, worker overrides, structured graph introspection, competitive no-op latency and bounded metadata memory, I see no architectural requirement to retain Ninja as the executor. Specific native ecosystem integration would still matter. More explicit contracts can improve AI-DX; they do not erase measured dispatch costs.

The full primary suite and required 180-observation exact-release/original/final control are independently accepted. Controlled tiny10k full time/RSS has recovered: final 14.976s, versus release 16.676s and original 20.976s; original-relative RSS is 47.25% lower. Heavy native no-op retains 46.35% release-relative wall improvement but remains 11.90% slower than original with 15.87% less RSS. Tiny 10k no-op is 22.18% faster than release and 2.73% faster than original, with 41.62% less original-relative RSS. These are bounded descriptive comparisons; five full-build samples per source do not establish significance. Preserve the remaining original-heavy-no-op tradeoff alongside recovered memory/full-dirty time. These results leave the direct AI-DX choices above unchanged: explicit programmable contracts favor Nift for bespoke agent-maintained workflows, while latency-sensitive native executor graphs and native toolchain integrations still favor established native tooling today. Global release/publication decisions remain parent-owned after all-eight review.

The heavy no-op tradeoff is consistent in matched rounds: final wall/CPU exceed original in 28/30 pairs, despite lower RSS in every pair. It is meaningful for latency-sensitive incremental use, not dismissed as measurement noise. The build-only release recommendation is a bounded non-blocker because every matched release-relative wall/CPU pair improves and full-dirty/RSS recovery passes; global release policy remains separate.
