# Practitioner assessment — draft, no Labs publication

I would choose Nift for bounded filesystem work already integrated into a Nift project, particularly where `.f` policy and explicit artifact/lifecycle contracts improve agent-maintained automation. This refresh certifies the adapters and correctness; it does not establish Nift as the preferred bulk-filesystem executor. For new throughput-heavy tree processing, the measured Go/Bun/Node implementations remain substantially faster, and native metadata/SHA-256 availability matters.

At 10000 inputs in the booted boundary, Nift walk was184.959 ms against Bun26.515; stat269.615 against Bun69.629; portable checksum reads10188.374 against Go212.571; no-dirty mirror21433.438 against Go461.194. These are equivalent exact-output contracts implemented with each runtime's own APIs, not pure disk bandwidth or a universal language ranking. The read/mirror checksum loops include policy/interpreter work. The separate stat-before-select filter supplement similarly leaves a substantial gap: extension selection at100000 inputs3628.238 ms against Bun555.903. Tables remain separate for different boundaries/contracts.

Agent-primary explicitness remains useful: declared inputs, output ownership, lifecycle and invalidation can be mechanically verified. Eliminate duplicated metadata with helpers without hiding those distinct semantics. Human-primary concerns include convenient native filesystem APIs and recovery/error ergonomics; performance is not the sole authoring criterion.

Current missing native SHA-256/stat timestamps and recursive directory removal remain capability gaps, not timings of failed implementations. Exactly-once inline/bound execution and edge-path correctness gates passed. Raw wait4 memory has an inherited supervisor floor, so this draft makes no runtime memory ranking. Historical cross-host differences are descriptive; targeted same-node diagnostics, if warranted, must be separate and cannot replace these accepted observations.
